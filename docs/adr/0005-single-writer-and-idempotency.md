# ADR 0005 — Single writer into the ERP, and idempotency

- Status: accepted
- Date: 2026-08-24

## Context

A commerce platform retries. Networks time out after the ERP has already committed, users double-submit, queues redeliver, and operators replay a dead-letter queue after an incident. Without an explicit design, every one of those produces a duplicate order — the most expensive class of bug in this system, because it is discovered by the customer and corrected by a human.

## Decision

### One writer

`order-gateway` is the only component in the platform permitted to write to Business Central. Every other service reads. A service that needs a write raises an intent that the gateway owns.

This is not a style preference: it is what makes the write path auditable and what makes the idempotency guarantee below enforceable in one place rather than assumed in five.

### Every write carries a caller-generated idempotency key

The key is generated by the originating business action — a checkout submission, a quote conversion — not by the transport. It is stable across every retry of that same action, and it travels the whole path: platform outbox, integration layer, ERP staging table.

The connector persists the key with the resulting document number. A second arrival with a known key returns the original result and does not create a document. The check is a database uniqueness constraint, not an application-level lookup — an application check between two concurrent retries has a race, a unique index does not.

### Writes are staged, never synchronous

The platform writes the intent to its own outbox inside its own transaction and returns. Delivery, retry and backoff happen outside that transaction. Business Central does the mirror image: the staging table row is written and committed, and a background session posts it. No outbound HTTP call is ever made while a posting transaction holds locks.

### Retry state is data

A staged row carries `status`, `attempts`, `lastError` and `nextRetryAt`. Retry is a scheduled read over that table, not a sleeping loop, and a row that exhausts its attempts moves to a terminal state that a human can see and act on. Failures are visible rows, not lost messages.

## Consequences

- The order contract is asynchronous. `POST /orders` returns `202 Accepted` with a platform-side identifier; the ERP document number arrives later on the status projection. The storefront must be built for this from the first screen — retrofitting an async confirmation into a UI that promised a synchronous order number is a rewrite.
- Correlation identifiers flow end to end, from the storefront request through the integration layer into ERP telemetry, so one identifier answers "what happened to this order".
- The gateway is a availability-critical component and needs the operational attention that implies.
